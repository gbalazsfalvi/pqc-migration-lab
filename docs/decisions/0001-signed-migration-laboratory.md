# ADR 0001 · Keep protocol, application trust and public evidence separate

- **Status:** Accepted for the local laboratory
- **Date:** 2026-11-13
- **Scope:** Milestones 01–05A
- **Decision owners:** Project maintainers

## Context

A migration reference needs more than a successful signature call. It must show how algorithm requirements interact with identity, freshness, retries, durable business results and changing keys.

It must also be reproducible on a developer's machine, use public synthetic fixtures and avoid implying production guarantees that a local experiment cannot establish. Benchmarking and functional demonstrations answer different questions.

## Decision

### Keep rules inward and adapters explicit

The dependency-free protocol module owns immutable envelope concepts, framing and signing/verification ports. JCA and JSON adapters implement those boundaries. The integration core adds receiver policy, signed claims, trust snapshots and ledger ports without depending on Spring, JCA or persistence technology.

The Boot application is the composition boundary. The React client presents actual Java observations; it does not implement verification or choose a weaker live receiver requirement.

### Use one process with real HTTP and separate capabilities

Two Boot contexts start actual loopback servers. The receiver is supplied independently imported public verifiers and metadata; private signing and lifecycle capabilities remain on the publisher side.

One JVM makes a shared read/write trust lease possible. A receive operation holds that lease through its durable commit, so a completed revocation applies to subsequent operations. This is a logical capability boundary, not process isolation or a distributed trust protocol.

### Define dual verification as an application requirement

Ed25519 and ML-DSA-65 sign the same DSSE-framed original payload. BOTH_REQUIRED accepts only when both algorithms verify for the configured owner. This is an explicit application policy, not a claim that DSSE itself mandates those algorithms or that the project implements a standardized composite-signature format.

Wire key hints never establish trust. Signed issuer, audience and time are validated after cryptographic requirements. Every retry is verified against current trust before durable idempotency is consulted.

### Persist facts and key state with different responsibilities

The H2/Flyway ledger atomically stores one release and its original acceptance evidence per issuer/event ID. Historical receipts remain facts even when a signing generation is later revoked.

The publisher's authenticated encrypted local vault persists active private keys and public generation history. A separate owner-only account secret unlocks it. Rotation drops old private encodings, retains a fixed verification overlap and publishes a complete dual generation only after persistence succeeds.

This design does not claim external rollback prevention, hardware isolation or secure erasure.

### Treat the demonstration as an observer

Milestone 05A creates its own temporary runtime workspace and independent secret. It uses fixed public HTTP routes, actual transport bytes and two complete runtime reconstructions. Only public envelopes, metadata and receipts cross those reconstruction boundaries.

Reports include actual statuses, reasons and semantic assertions. Unexpected response fields stop raw export; exceptions are reduced to fixed categories. A fail-fast interruption yields partial evidence rather than fictional future observations.

The public report directory contains no runtime database or vault. A checksum manifest identifies the generated bytes; it is intentionally not presented as independent report provenance.

## Alternatives considered

| Alternative | Tradeoff and reason for this decision |
| --- | --- |
| A single controller calling the receiver directly | Simpler, but would omit the actual HTTP transport and obscure capability separation |
| Separate containers/services from the outset | Better process isolation, but increases local prerequisites; defer until distributed operation is itself in scope |
| Browser-side cryptographic verification | Adds another trusted implementation and can disagree with the receiver; Java remains authoritative |
| Accepting a stored receipt before revalidation | Faster retry path, but would allow old acceptance to bypass revocation or a stronger policy |
| Keeping old private keys through verification overlap | Convenient for signing historical generations, but verification needs public material only |
| Reusing the interactive data directory in the demo | Easier startup, but makes demonstrations destructive or dependent on prior user activity |
| Freezing the demo clock | Deterministic timestamps, but would hide real freshness behaviour; use UTC and keep exact boundary tests separate |
| Combining functional timing with JMH conclusions | Attractive single report, but conflates cold startup, transport and cryptographic operation measurements |

## Consequences

The project has more explicit ports, DTOs and evidence types than a minimal signing example. Tests and architecture rules enforce the separation, while per-module coverage and strict compilation remain enabled.

A developer can run the complete story with one command after installing the documented toolchain. Fresh keys and identifiers vary; the acceptance/rejection invariants are repeatable.

Production hosting, operator authentication, independent report provenance, stronger key custody and multi-node trust coordination require new decisions. Public repository publication, licensing choices, deployment and a demo video remain separate future work.
